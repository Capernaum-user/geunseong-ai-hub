# 로컬 LLM

> 근성쌤 · AI 지식허브의 〈로컬 LLM〉 허브. 데이터를 클라우드에 보내지 않고 **내 장비 안에서** 모델을 돌리는 방법과 그 판단 기준을 모은다.

로컬 LLM은 GPT·Claude 같은 클라우드 API 대신, **내 컴퓨터(또는 사내 서버)에서 직접 모델 가중치를 실행**하는 방식이다. [[obsidian/index|Obsidian × 생성형 AI]]와 [[harness/index|하네스 엔지니어링]]에서 다루는 워크플로의 "엔진"을 외부로 내보내지 않고 손에 쥐는 선택지다.

## 왜 로컬 LLM인가

- **프라이버시**: 프롬프트와 문서가 외부 서버로 전송되지 않는다. 개인 메모, 고객 데이터, 미공개 사업 자료를 다룰 때 유출 경로 자체가 사라진다.
- **폐쇄망·오프라인**: 인터넷이 차단된 사내망, 보안 등급이 높은 환경, 비행기/현장처럼 연결이 불안정한 곳에서도 동작한다.
- **비용 구조**: 토큰당 과금이 없다. 초기 하드웨어 투자 후에는 호출량이 늘어도 한계비용이 0에 가깝다. 대량 배치 처리·반복 실험에 유리하다.
- **통제권**: 모델 버전이 임의로 바뀌지 않는다. 같은 가중치를 고정해 두면 결과 재현성이 보장되고, 라우팅·프롬프트·파인튜닝을 내가 전부 통제한다.
- **지연·의존성**: warm 상태에서는 네트워크 왕복이 없어 응답이 빠르고, 외부 서비스 장애에 영향받지 않는다.

## 언제 클라우드가 더 나은가

로컬이 만능은 아니다. 다음 경우엔 클라우드 API가 합리적이다.

- **최상위 추론 품질**이 필요할 때. 소형 로컬 모델(3B~7B)은 복잡한 다단계 추론·구조화 출력에서 흔들린다. (실측 사례: 7B 모델은 plan JSON 파싱은 안정적이었지만, 검토·검증 단계까지 매번 만족시키지는 못해 결과가 회차마다 갈렸다.)
- **장비 사양이 부족**할 때. 큰 모델일수록 VRAM·RAM·디스크를 많이 먹는다.
- **운영 부담을 줄이고 싶을 때**. 모델 업데이트·드라이버·런타임 관리를 직접 하지 않아도 된다.

실무에서는 **하이브리드**가 정답인 경우가 많다. 민감 데이터·대량 처리는 로컬, 고난도 추론은 클라우드로 라우팅하는 식이다.

## 어떻게 시작하나

가장 빠른 경로는 **Ollama**다. 설치 한 번으로 OpenAI 호환 엔드포인트(`http://localhost:11434`)가 뜨고, 기존 도구를 거의 그대로 붙일 수 있다.

1. 런타임 설치 → 모델 받기(`pull`) → 로컬에서 응답 확인
2. Obsidian Copilot, 에이전트 오케스트레이터 등 클라이언트의 **프로바이더를 로컬 엔드포인트로 전환**
3. 채팅 모델 + 임베딩 모델을 분리 지정(예: 생성은 `qwen2.5`, 임베딩은 `nomic-embed-text`)
4. 민감도·난이도에 따라 로컬↔클라우드 **폴백/라우팅** 설계

구체적인 설치·연결·프로바이더 선택 절차는 다음 노트에 정리했다.

## 핵심 개념 빠른 참고

| 구분 | 의미 | 메모 |
|---|---|---|
| 가중치(weights) | 모델 본체 파일 | 클수록 품질↑·자원↑ |
| 양자화(quantization) | 가중치를 압축(예: Q4_K_M) | 메모리 절약, 품질 약간 손실 |
| 컨텍스트 길이 | 한 번에 다루는 토큰 수 | 긴 문서 처리 한계 결정 |
| 임베딩 모델 | 텍스트→벡터 변환 | RAG·의미검색의 엔진, 생성 모델과 별도 |
| OpenAI 호환 API | `/v1/chat/completions` 규약 | 로컬 서버가 이를 따르면 기존 SDK 재사용 |
