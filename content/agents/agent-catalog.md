# 에이전트 카탈로그 — 무엇이 있고, 어떻게, 왜 쓰는가

"AI 에이전트"는 한 종류가 아니다. 혼자 도구를 쓰며 일하는 **단일 코딩 에이전트**부터, 한 작업을 잘게 나눠 맡기는 **서브에이전트**, 여러 에이전트를 줄 세우는 **오케스트레이터**, 그리고 이들을 외부 도구·데이터에 연결하는 **MCP**까지 층위가 다르다. 이 노트는 직접 운영하며 정리한 분류를, "무엇 / 어떻게 / 왜"의 세 질문으로 풀어 쓴 카탈로그다.

> 함께 보기: [[ai-agent-roles|AI 에이전트 역할 (Claude·Gemini·Codex)]] · [[agent-decision-escalation|에이전트 의사결정과 에스컬레이션]]

## 한눈에 보는 분류

| 유형 | 한 줄 정의 | 대표 예 | 쓰기 좋은 상황 |
| :--- | :--- | :--- | :--- |
| 코딩 에이전트 | 터미널·파일·셸을 직접 쓰며 일하는 단일 실행체 | Claude Code, Codex | 코드 작성·수정, 리포 탐색, 자동화 |
| 서브에이전트 | 부모가 떼어 준 하위 작업을 격리된 맥락에서 처리 | 병렬 탐색·요약 워커 | 작업 분할, 맥락 오염 방지, 병렬화 |
| 오케스트레이터 | 목표를 DAG로 쪼개 여러 에이전트에 배분·검증 | CLI/플래너형 엔진 | 다단계·다역할 워크플로우 |
| MCP 연결 | 에이전트를 외부 도구·데이터에 표준 규약으로 접속 | Obsidian·Drive·Gmail MCP | 볼트·문서·캘린더 등 실제 데이터 작업 |

## 1. 코딩 에이전트 (단일 실행체)

**무엇.** 사람의 지시를 받아 파일을 읽고 쓰고, 셸 명령을 돌리고, 결과를 보고 다음 행동을 스스로 정하는 한 개의 실행 루프다. Claude Code가 대표적이며, 같은 자리에서 Codex 계열도 코드 구현·테스트를 맡는다.

**어떻게.** 작업을 명확한 목표 한 줄로 주고, 도구 사용 권한(읽기/쓰기/실행)의 범위를 정해 둔다. 에이전트는 탐색 → 변경 → 검증 → 보고의 짧은 사이클을 반복한다.

**왜.** "검색해서 붙여넣는" 보조가 아니라, 리포 전체를 돌아다니며 맥락을 모아 끝까지 처리하기 때문에 반복적·기계적 구현 부담을 크게 덜어 준다. 단, 파괴적·외부 영향 작업은 반드시 사람 확인을 거치게 둔다([[agent-decision-escalation|에스컬레이션]] 규칙).

## 2. 서브에이전트 (작업 분할)

**무엇.** 부모 에이전트가 큰 작업을 떼어 내, **격리된 별도 맥락**에서 돌리는 하위 일꾼이다. 부모는 결과만 돌려받는다.

**어떻게.** "이 폴더만 조사해서 핵심만 보고" 같은 좁고 자족적인 과제를 여러 서브에이전트에 동시에 던진다. 서로의 중간 결과를 건드리지 않게 하고, 부모가 종합을 맡는다.

**왜.** (1) **맥락 오염 방지** — 탐색 과정의 잡음이 부모 대화를 더럽히지 않는다. (2) **병렬화** — 독립 작업을 동시에 굴려 시간을 줄인다. (3) **역할 격리** — 구현과 검증 세션을 분리해 자기 검증의 함정을 피한다(삼권분립: 구현자/검증자 분리).

## 3. 오케스트레이터 (다단계 워크플로우)

**무엇.** 하나의 목표를 받아 **DAG(방향성 비순환 그래프) 계획**으로 분해하고, 각 작업을 적합한 에이전트에 배분한 뒤 의존성 순서대로 실행·검증하는 상위 제어자다.

**어떻게.** 직접 정리한 CLI 오케스트레이터 설계 기준으로 보면 흐름은 이렇다.

1. **컨텍스트 수집(Retriever)** — 지식 저장소(볼트)를 훑어 관련 문서를 가져온다.
2. **계획(Planner)** — 목표를 작업 노드로 쪼갠다. 각 노드는 `id`, 담당 `agent_id`, 지시문, 선행 의존성(`depends_on`), `validation_criteria`를 갖고 스키마로 검증된다.
3. **실행(Executor)** — 위상정렬로 순서를 정해 순차 실행하고, 결과·상태를 기록한다.
4. **가드/안전 게이트** — 파일 쓰기는 허용된 작업 폴더로만 제한하고, 출력에 API 키·토큰·인증서가 섞이면 거부한다. 실패 시 복구 지침과 세션 포인터를 남긴다.

**왜.** 단일 에이전트로는 흐트러지기 쉬운 다단계·다역할 작업을, "계획 → 분배 → 검증"의 결정론적 틀에 얹어 **재현 가능하고 감사 가능한** 실행으로 만든다. 안전 게이트를 파이프라인에 내장하면 사람이 매번 감시하지 않아도 위험 행동이 차단된다.

## 4. MCP 연결 (외부 도구·데이터 접속)

**무엇.** MCP(Model Context Protocol)는 에이전트를 외부 도구·데이터 소스에 붙이는 표준 규약이다. 에이전트가 "무슨 도구가 있고 어떻게 부르는지"를 공통 형식으로 알게 해 준다.

**어떻게.** Obsidian 볼트 읽기/쓰기, Google Drive·Gmail·캘린더, 다이어그램 도구 등을 MCP 서버로 연결해 두면, 에이전트가 같은 인터페이스로 실제 데이터를 다룬다. 자격증명은 노트가 아니라 설정 계층에 두고 절대 본문에 적지 않는다.

**왜.** 에이전트의 능력을 모델 안에 가두지 않고 **내 실제 작업 환경**(지식베이스·문서·일정)으로 확장한다. 도구마다 일회성 통합을 짜는 대신 한 규약으로 붙이므로, 새 도구 추가 비용이 낮다.

## 운영 원칙 — 카탈로그를 안전하게 굴리는 법

- **역할을 고정한다.** 누가 계획(Planner)·구현(Creator)·검증(Tester)인지 분명히 하고 세션을 격리한다. 같은 에이전트가 만들고 자기를 검증하지 않게 한다.
- **자율 구역과 에스컬레이션 구역을 가른다.** 되돌릴 수 있고·범위가 명확하고·보안/데이터/외부 영향이 없는 일만 무확인 실행. 하나라도 걸리면 사람 확인. 자세한 게이트는 [[agent-decision-escalation]] 참고.
- **안전 게이트를 코드로 박는다.** 파일 쓰기 범위 제한, 키·토큰 누출 스캔, 실패 복구 포인터는 사람의 주의력이 아니라 파이프라인이 보장하게 한다.
- **더 엄격한 규칙이 이긴다.** 규칙이 충돌하면 보안·원본보존·사용자지시·검증을 편의보다 앞세운다.
